## What we're building
A Solana memecoin whose trading fees fund group "breaks" of Collector Crypt gacha packs. On the website, players buy paid spots in USDC; some spots in every break are **free for coin holders**, drawn by verifiable randomness. At the deadline the keeper buys one pack per spot, pulls them all, and the pulled cards are randomly assigned across the spots and sent to the winners' wallets. Winners keep a card or sell it back on Collector Crypt. Everything runs automatically: break scheduling, draws, pack buying, delivery, website, and an X bot.

### Problems this design fixes (vs. the old model)
1. Big breaks stalled when fee volume was low → fees accumulate in a **treasury reserve**; breaks are only created when the reserve can fund them.
2. Breaks stayed open for hours waiting to fill → **fixed deadline**; an unfilled paid spot is simply not bought, so the pool is smaller. Nothing ever waits.
3. Non-payers had no way in → **free holder spots** in every break.

## Core rules (product decisions — don't change without asking)
- **Chain:** Solana. Programs in Anchor (Rust). Off-chain in TypeScript.
- **Fees:** launchpad creator fees land in a Squads multisig; the keeper sweeps them into the treasury program, which splits them into buckets:
  - `subsidy` (default 70%): tops up the cost of paid spots (if `spot_price < pack_price`)
  - `holder` (default 30%): pays for free holder spots
  - Split is a config value set by admin (multisig).
  - Fees arrive in SOL; the keeper swaps to USDC (Jupiter, slippage cap, per-sweep size cap) before depositing. The treasury is USDC-only.
- **Breaks are fee-funded from the first one.** No team pre-funding. A break can only be created when the buckets can cover its worst case:
  `free_spots × max_pack_price + paid_spots × max(0, max_pack_price − spot_price)` (all paid spots fill). The first break auto-opens as soon as the reserve crosses that threshold; the second the same way. The site shows a public progress bar ("Break #1 unlocks at $X — currently Y%"). With no vault or inventory to buy first, break #1 unlocks at pack cost, not prize value.
- **Break shape:** `paid_spots` (max, e.g. 10), `free_spots` (e.g. 2–4), `spot_price` in USDC, `pack_machine` (one Collector Crypt machine/price tier per break, so every spot is equivalent), `max_pack_price`, `opens_at`, `closes_at` (6–24h window).
- **At the deadline:** pool size = filled paid spots + free spots (fewer if too few holders are eligible). The keeper buys exactly one pack per spot and pulls them. Unfilled paid spots are not bought. No house fills.
- **Shared pool:** all pulled cards go into one pool and are randomly assigned across the spots. This stops the keeper from steering a good pull to a chosen wallet. Spots are ordered: paid by purchase order, then free spots in draw order.
- **Pack randomness is Collector Crypt's.** Each pull uses Collector Crypt's on-chain VRF (per Jupiter's docs, with a per-pull proof). Our randomness covers only the free-spot draw and the card-to-spot assignment.
- **No staking (for now).** Free-spot eligibility = holding, measured by **time-weighted average balance (TWAB) over the break window** (`opens_at` → `closes_at`).
  - Minimum TWAB to be eligible (e.g. 1M tokens — config).
  - Weight = TWAB, **capped per wallet** (config) so whales can't dominate and splitting wallets gives no edge.
  - Exclude: LP pools, exchange wallets, team wallets, flagged bundle/sniper wallets. Exclusion list is public.
  - Staking may be added later as an extra weight multiplier — keep the eligibility module pluggable.
  > PENDING APPROVAL (A2): the cap rewards splitting (10× the cap in one wallet = 1× weight; split into ten wallets = 10×). Proposal: linear weight (no cap or a high sanity cap), keep the min TWAB, one spot per wallet, and merge wallets funded from the same source into one entity (published, with reason codes).
- **Randomness: ORAO VRF** (decided by the owner). One request per break, after `closes_at`, and **after both the eligibility root and the pool hash are committed**. See "Randomness" below. (Switchboard was dropped: news reports say it shut down on 2026-09-25.)
  > PENDING APPROVAL (A4): add a `challenge_period` (30–60 min) between `commit_eligibility` and `request_randomness`. The multisig may void the root (max 2 re-commits) while no seed exists yet.
- **Everything verifiable:** `pack_machine` and `max_pack_price` committed at creation, eligibility root and pool hash committed before the draw, randomness proof stored, all derivations deterministic. The site shows a per-spot ledger: pack purchase tx → Collector Crypt VRF proof → assignment → delivery tx.
- **Known trust gap (MVP):** the chain cannot prove the keeper really bought every pack or delivered every card. The per-spot ledger makes any gap publicly visible. A tighter option is listed in Phase 0.

## Draw algorithm (deterministic, documented on the site)
Implemented in `draw-core/` (pure Rust, shared by the `breaks` program and its tests). `draw-core/vectors.json` holds a fixed example with every output; the TypeScript keeper and the "verify this draw" tool must reproduce it byte for byte (the Rust test fails when the file is stale).
- **Hash:** SHA-256 everywhere (the Solana syscall on-chain).
- **Eligibility tree (Merkle sum tree):** leaves are `(wallet, weight)`, sorted by wallet bytes ascending, strictly increasing (no wallet twice), weight > 0. Leaf hash `H(0x00 ‖ wallet(32) ‖ weight u64 LE)`, sum = weight. Inner hash `H(0x01 ‖ left.hash ‖ left.sum u64 LE ‖ right.hash ‖ right.sum u64 LE)`, sum = left + right (overflow = invalid). An odd node at the end of a level is carried up unchanged (never duplicated, which would count its weight twice). The root hash is committed in `commit_eligibility`, with `total_weight` = root sum. A proof is a list of `(sibling hash, sibling sum, sibling_is_left)`; it proves the leaf's range `[start, start + weight)` in `[0, total_weight)`, where `start` is the sum of the left siblings. So the keeper cannot hand-craft ranges.
- **Free-spot winners, drawn without replacement.** Winner `i` (0, 1, …): `remaining = total_weight − Σ weights of earlier winners`; `r = u128_le(H("breaks:free:v1" ‖ seed ‖ i as u16 LE)[0..16]) mod remaining`; then walk the earlier winners' ranges in ascending order of start and do `if r >= start { r += weight }`; the winner is the leaf whose range contains `r`. This always yields `min(free_spots, eligible)` distinct wallets however skewed the weights are (this replaces the earlier "retry with a nonce, give up after 32 tries" rule, which could fail when one wallet holds almost all the weight, after the pool size was already fixed).
- **`claim_free_spot(index, wallet, weight, proof)`** is permissionless (the keeper submits it) and **in order**: the program recomputes where winner `index` lands, checks the proof against the committed root and total weight, checks the wallet's range contains the drawn position, and records the winner. A wallet that appears in two leaves of a bad tree is refused the second time. When the last winner is recorded the break is `Drawn`; with no free winners it is `Drawn` as soon as the seed is final.
- **Card → spot assignment** (off-chain, anyone can recompute): the pool sorted by card mint (so pull order can't matter); spots are ordered paid spots by purchase order, then free spots in draw order. Fisher–Yates from the back: for `k` from `n−1` down to 1, `j = u128_le(H("breaks:items:v1" ‖ seed ‖ k as u16 LE)[0..16]) mod (k+1)`, swap positions `k` and `j`. Spot `s` gets the card at index `perm[s]` of the sorted pool.
- The eligibility commit also includes `inputs_hash` of the published `balance_events` snapshot, so anyone can recompute TWAB.
- Limits: at most 16 free spots per break (the winner list is stored in the break account); a proof is at most 40 steps, in practice about 14 for thousands of holders, which fits a transaction.

## Randomness

- **Provider:** ORAO VRF, program `VRFzZoJdhFWL8rkvu87LpKM3RbcVezpMEc6X5GVDr7y` (same address on mainnet and devnet). ORAO's Rust crate targets Anchor 0.32, so we do not use it: `programs/breaks/src/randomness.rs` builds the `request_v2` instruction by hand and reads the request account's bytes. Both layouts are pinned by tests against fixtures generated with the real `orao-solana-vrf` 0.7.0 crate.
- **Flow:** `request_randomness` (seed = `sha256("breaks:randomness:v1" || break || attempt || eligibility_root || pool_hash)`) → ORAO's oracles write 64 bytes (an Ed25519 signature of the seed) into the request account → `settle_randomness` stores `sha256("breaks:seed:v1" || those 64 bytes)` as the draw seed. Anyone can check the 64 bytes against ORAO's public key.
- **Why the seed is safe:** it cannot be known before the eligibility root and the pool hash are committed, so nobody can prepare an answer for it. If a stranger asks ORAO for the same seed first, `breaks` adopts that request.
- **Cost:** ORAO charges a request fee (SOL, or ORAO tokens if its network state is configured that way). The keeper wallet pays it; for token fees the keeper passes ORAO's token accounts as extra accounts.
- **Tests:** `programs/mock-orao` is a TEST-ONLY stand-in with ORAO's `request_v2` interface and account bytes, where anyone can fulfil with any value. It is never deployed with real money. Not yet tested: the real ORAO program itself. Plan: a CI job that dumps ORAO's program and network state from devnet, loads them into LiteSVM, swaps in a test fulfilment authority and runs the same flow with a real signature.
- **Trust left:** ORAO's oracle set (a Byzantine quorum of its authorities) and the ORAO program upgrade authority. The admin can switch to another program with the same interface via `set_randomness`.

## Architecture

### 1. On-chain programs (`programs/`)
**`treasury`**
- `initialize(config)` — admin = Squads multisig; only the program's upgrade authority can call it.
- `deposit_fees(amount)` — splits into `subsidy` / `holder` buckets by config ratio.
- `set_split(subsidy_bps, holder_bps)` — admin only.
- `set_controller(controller)` — admin only. The controller is the `breaks` program's `treasury_authority` PDA.
- `lock_funds` / `unlock_funds` / `pay_from_locked` — controller only. Locking is how the on-chain funding rule works (the treasury refuses unless the bucket has that much unlocked). Pay-outs can only come out of locked funds, so they never touch money reserved for another break.
- Read-only balances for the website: the two vault balances and `locked_subsidy` / `locked_holder` in the config account.

**`breaks`** (built: the whole on-chain flow up to the recorded draw)
- `initialize(params)` — upgrade authority only. Config: admin, keeper, buyer wallet, window and spot limits, pause.
- `set_keeper`, `set_buyer`, `set_paused` — admin only. Pausing stops new breaks, new spots and `fund_purchases`; cancel and refunds always work.
- `create_break(params)` — keeper; locks `paid_spots × (max_pack_price − spot_price)` of subsidy and `free_spots × max_pack_price` of holder funds in the treasury (the funding rule). `spot_price ≤ max_pack_price` is enforced: a markup is not supported yet.
- `buy_spot(index)` — USDC into the break's escrow; one spot account per spot, `index` must be the next free one.
- `close_break` — anyone, after `closes_at`.
- `commit_eligibility(root, total_weight, entry_count, inputs_hash)` — keeper, after close.
- `fund_purchases` — keeper. Pays `pool_size × max_pack_price` to the buyer wallet (escrow + locked subsidy + locked holder funds) and returns the unused locks. The destination is fixed to the configured buyer wallet. **This is the step users trust.** `pool_size` = sold paid spots + `min(free_spots, entry_count)`; an empty pool cannot be funded and is cancelled instead.
- `commit_pool(pool_hash, pool_size)` — keeper, after funding; `pool_size` must match.
- `cancel_break` — admin, before funding; `refund_spot` — anyone, pays the spot's owner.
- `request_randomness` — keeper, after the pool is committed. Asks ORAO for randomness with a seed that commits to the break, the attempt, the eligibility root and the pool hash. The keeper pays ORAO's request fee. If someone already asked ORAO for the same seed, the request is adopted instead of failing. A request that ORAO never answers can be repeated after `randomness_timeout_secs` (at most 5 attempts), but never once it has been answered.
- `settle_randomness` — anyone, once ORAO has answered: stores the seed of the draw (`sha256("breaks:seed:v1" || ORAO's 64 bytes)`). Final.
- `set_randomness(program, timeout_secs)` — admin only: which VRF program to use (ORAO's address in production) and the repeat timeout.
- `claim_free_spot(index, wallet, weight, proof)` — anyone, once the seed is final; records the free-spot winners in order (see "Draw algorithm"). Status flow: … `PoolCommitted` → `RandomnessRequested` → `Settled` → `Drawn`.
- Next: the keeper side of the pipeline (pack buyer, delivery). Open: what happens to buyer-wallet money that is not spent (return path), and the partial-failure policy.

No vault program. Cards pass through the buyer wallet. An on-chain escrow for cards is only added if Phase 0 shows it is possible.

### 2. Keeper (`keeper/`, TypeScript, runs on a server)
**Built so far (tested; wired into up to six jobs with mock providers; never run against a real node):**
- `src/draw/`: TypeScript port of `draw-core` (sum tree, free-spot draw without replacement, card assignment). Tests reproduce every case in `draw-core/vectors.json` generated by the Rust code, and fail if either side changes.
- `src/eligibility/twab.ts`: TWAB from the indexed token transfers. An owner's balance at time `t` is the sum over its token accounts of the balance after each account's last event at or before `t`; TWAB = integral of that over the window divided by the window length (whole token base units, rounded down, exact bigint math). The opening balance of an account is `balance_after − delta` of its first event, so a history that starts mid-way works; a history where `delta` does not lead to `balance_after` is rejected. Events of one token account in one slot are put in the order that chains (`chainOrder`), since the data does not say which transaction ran first.
- `src/eligibility/eligibility.ts`: who is eligible and with what weight (minimum TWAB, optional cap per wallet = pending decision A2, public exclusion codes, program-derived addresses excluded by default), the sorted leaves for the tree, the rows for `twab_snapshots` with a reason for every wallet that is out, and `inputs_hash`.
- `inputs_hash` = `sha256` of the text `breaks:inputs:v1,<window start>,<window end>` followed by one line per balance event in chronological order (`signature,slot,time,owner,tokenAccount,delta,balanceAfter`), each line ending in `\n`. That text is what gets published next to the eligibility list.
- `src/draw/pool.ts`: `pool_hash` = `sha256("breaks:pool:v1" ‖ mint_0 ‖ mint_1 ‖ …)` over the pool sorted by mint (32 bytes each, no duplicates), and `assignCards` (spot → card, paid spots first, then free spots in draw order).
- `src/solana/pubkey.ts`: base58, on-curve check, and PDA derivation checked against the real Solana values for every PDA the programs use.
- `src/solana/`: instruction builders and account decoders for both programs (`treasury.ts`, `breaks.ts`; Borsh `codec.ts`; shared `instruction.ts`). A builder returns `{programId, accounts: [{pubkey, isSigner, isWritable}], data}` and derives every PDA itself; the caller only passes wallets, token accounts and the two program ids (`Programs`). `breaks.ts` also has `requestId`, `drawSeed`, the ORAO request address and `decodeRequest` (same checks as the program), and decoders for `Break`, `BreaksConfig`, `Spot` and the treasury `Config`.
- **Instruction vectors:** `programs/<name>/instruction-vectors.json` is generated by the Rust tests (`programs/<name>/tests/instruction_vectors.rs`, no SBF build needed; `UPDATE_VECTORS=1 cargo test -p treasury -p breaks --test instruction_vectors` rewrites them, a plain run fails when they are stale). `keeper/test/instructions.test.ts` rebuilds every case (data bytes, account order and signer/writable flags) and decodes every sample account, and fails on a vector it has no builder for. Change an instruction or account in Rust → regenerate the vectors → the TypeScript test shows what to change.
- `src/packs/`: the pack buyer, written against the `PackProvider` steps (`findExisting`, `prepare`, `submit`, `status`, `reveal`; `provider.ts`) because the real Collector Crypt purchase flow is unknown until Phase 0 is done. `buyer.ts` (`PackBuyer.buyBreak`) runs one pack per index through `planned → submitted → confirmed → pulled` and keeps its notes in a `PackStore` (`store.ts` in memory, `sql-store.ts` over `packs` + `pack_attempts`, migration 0002; one contract test runs against both). The rules that make a double-buy impossible, each pinned by a test that fails when the rule is removed:
  - the attempt (signature and expiry) is saved BEFORE the purchase is sent (`startAttempt` is a compare-and-set, so two workers cannot both buy an index);
  - a new purchase is built only when the saved one reverted or is `expired` (provider says: past its expiry and certainly never landed; otherwise `pending`), and only after the wallet history was searched for the index's memo (`packMemo`);
  - the provider's price is re-checked against `max_pack_price`; a live price above the cap buys nothing and the pack waits;
  - a pack bought twice is reported (`BreakProgress.anomalies`, `PackRow.lastError`), never hidden; a pack that reverts `maxAttempts` times is `failed` and the buyer does nothing more with it (the partial-failure policy is still open).
  - `MockPackProvider` is a pretend chain (signatures before sending, block-height expiry) with injectable failures: `drop`, `throw`, `land-then-throw`, `revert`. `packBuyerJob` wraps the buyer for the runner; it needs a `BreakSource` (funded breaks → `BreakPlan`, progress report), which the pipeline provides.
- `src/delivery/`: sends each pulled card to the wallet the draw assigned it to, written against the `CardTransfer` steps (`ownerOf`, `prepare`, `submit`, `status`; `transfer.ts`) because how a Collector Crypt card moves (pNFT rule set, Core asset, whether it can still be sold back) is a Phase 0 answer. Same shape as the pack buyer (`deliverer.ts`, `store.ts` in memory + `sql-store.ts` over `deliveries` + `delivery_attempts`, migration 0003, one contract test for both stores, `MockCardTransfer`, `deliveryJob`). A wrong recipient cannot be undone, so:
  - `plan.ts` (`buildDeliveryPlan`) works out who gets which card only from what the chain committed, and throws a `PlanError` naming the first thing that does not add up: break not `Drawn`, empty seed, paid spots that do not match `spots_sold` (order, break, refunded), free winners that do not match `pool_size − spots_sold`, a pool that is not exactly the committed size, or whose `poolHash` is not the one committed before the draw. The assignment is `assignCards` (the verified Fisher–Yates), so the order the cards were pulled in does not matter.
  - the chain is the source of truth for where a card is: nothing is sent unless the buyer wallet owns it; a card already at its recipient counts as delivered (`adopted`, no signature); a card in any other wallet stops that delivery and is reported in `DeliveryProgress.anomalies`; a transfer reported confirmed whose card is not at the recipient is a failure, not a success;
  - the transfer the provider built is checked against the plan (recipient, card, sender) before anything is saved or sent; the attempt is saved before the send; a new transfer is built only after the saved one reverted or can never land;
  - if the plan for a spot ever differs from the recorded one (`PlanChangedError`), that delivery stops.
  - Not done: tracking Collector Crypt's sellback deadline (about 72 h from the pull) waits for Phase 0 to confirm it; the `deliveries.sellback_deadline` column stays empty.
- `src/pipeline/`: drives a break from the end of its sale to the draw being recorded, and connects the pack buyer and the deliverer to the chain. `pipeline.ts` (`BreakPipeline.advance`) starts every call from the on-chain `Break` status, never from notes of its own, so it is safe to call as often as you like: `Open` → `close_break` (5 s after `closes_at`, so a keeper clock ahead of the chain's does not waste a transaction), `Closed` → `commit_eligibility` with what the eligibility planner returns (or wait for it), `EligibilityCommitted` → `fund_purchases` only when the program is not paused, the pool is not empty (otherwise the admin must cancel), the stored eligibility list is exactly the committed one (the free winners are claimed from it, so money does not move without it) and the buyer wallet's USDC account exists; `Funded` → `commit_pool` (only when every pack is pulled, no pack failed, the pool has exactly `pool_size` distinct cards and the buyer wallet holds each of them), `PoolCommitted` → `request_randomness` (seed = `requestId(break, attempt, root, pool_hash)`), `RandomnessRequested` → `settle_randomness` once ORAO answered, or a repeat (attempt + 1, previous request passed) after `randomness_timeout_secs` and never more than 5 attempts and never once answered, `Settled` → `claim_free_spot` one winner at a time in order. Before claiming it rebuilds the tree from the stored eligibility list and refuses to go on unless the root, total weight and entry count equal what was committed, and it checks that winners already recorded are the ones the draw gives. A send whose result is unknown is not repeated for `resendAfterMs`. The pipeline refuses to ask a randomness program other than the configured one. `sources.ts`: `FundedBreaks` (a `BreakSource` for the pack buyer: the plan comes from the chain) and `DrawnBreaks` (a `DeliverySource`: reads the `Spot` accounts, the buyer wallet and the pulled cards and calls `buildDeliveryPlan`; marks the break `delivered` when every card is out). `job.ts`: `pipelineJob`, which also mirrors the chain status into `breaks.status` (migration 0004 adds `drawn`). `repo.ts` (`SqlBreakRepo`), `eligibility-store.ts` (`SqlEligibilityStore`, the eligible rows of `twab_snapshots`). The chain is behind the `ChainClient` port (`getAccountData`, `sendAndConfirm`).
  - Tested against `test/support/mock-chain.ts`, a TypeScript MODEL of the nine instructions the keeper sends (the treasury's `deposit_fees` and `create_break`, `close_break`, `commit_eligibility`, `fund_purchases`, `commit_pool`, `request_randomness`, `settle_randomness`, `claim_free_spot`; USDC movements are not modelled, except the treasury's vault balances and locks that `create_break` and `fund_purchases` change, and the sweep wallet's SOL and USDC that `deposit_fees` moves), following the Rust handlers (it reads the real instruction bytes with the real decoders and checks the real proofs). It is not the program: the program itself is only tested by the LiteSVM tests in CI, and the keeper against the real program and the real ORAO is still untested. The test account encoders (`test/support/accounts.ts`) are checked against the bytes the Rust program writes.
- **Eligibility planner** (`src/eligibility/planner.ts`, migration 0005): from the indexed token balances to the values `commit_eligibility` takes, with the public record of how. `SqlEligibilityPlanner.plan` (1) returns the stored list if there is one; (2) otherwise waits until the balance indexer has read `INDEXER_SETTLE_SECS` past the end of the window (`indexer_state`; a quiet token has no events to show progress, so the indexer must record it itself), never computing from a history that may still grow; (3) takes `balance_events` before the window end and the active `exclusions`, builds the list (`buildEligibility`, `MIN_TWAB`, optional `WEIGHT_CAP` = pending A2), publishes the full record (every wallet's TWAB, weight and reason, and the exact balance-event text that `inputs_hash` commits to) through a `Publisher` (`DbPublisher`: `published_documents` addressed by SHA-256, URIs `db:sha256:<hex>`; IPFS/Arweave later behind the same port), and stores `twab_snapshots` and then `eligibility_lists` (the list row last, so its existence means everything before it was written). Every later call returns the stored values, so a retry commits exactly what was published even if the exclusions changed. `committed()` is a read-only lookup (used before funding). An empty list is a zero root, zero weight and zero entries (the program requires weight and count to be zero together). Assumes one keeper process drives a break.
- **Balance indexer** (`src/indexer/`, migration 0006): fills `balance_events` and `indexer_state` from plain JSON-RPC (`getSignaturesForAddress` and `getTransaction` with `jsonParsed`, finalized data only; `RpcTokenReader` works against any node or provider URL, nothing is vendor-specific). **How it stays complete:** tokens of a mint reach a token account only from the mint (mint-to) or from another token account of the mint, and every such transaction names both. So reading the mint and then every token account that shows up in what it reads, each from its first transaction (`TokenIndexer`), reads every transfer; there is no separate discovery step. It starts at the mint's first transaction, so it has to run from the token's launch (history is not skipped; a snapshot start could not be recomputed by others). `parse.ts` (`readTransaction`) turns a transaction into balance events from the node's pre/post token balances (exact base units; a closed account ends at 0, a new one starts at 0; a change of owner is two rows, which is why migration 0006 puts the owner in the unique key) and throws on what it cannot read exactly (a balance without an owner, no block time) instead of guessing. Work is cut into steps (one page of signatures of one address, `INDEXER_PAGE_SIZE`), each saved before the next in `indexed_accounts` (cursors `until_sig` / `resume_before` / `pass_newest`), within a call budget per run (`INDEXER_CALLS_PER_RUN`). The order inside a step is: note the accounts the page names, store its events, save the cursor, so a crash repeats work and never skips it (a stored transaction is not fetched again, so its accounts must be noted first). A finished pass sets `covered_until` = pass start − `INDEXER_LAG_SECS` (finalization lag and clock skew); `indexer_state.indexed_until` is the smallest `covered_until` over the accounts that may hold tokens, held while any of them has never been read, and never moving back. An account whose newest-slot balance is empty is left alone (`active = false`) until a transaction gives it tokens again. Every address is read again each `INDEXER_INTERVAL_SECS`, and at once when a break (status `open`/`closed`, no stored list) has a window end + `INDEXER_SETTLE_SECS` that is safely past. Cost: about one `getSignaturesForAddress` per holder per interval plus one `getTransaction` per token transaction; someone who spreads dust over many accounts adds accounts to read at their own SOL cost (not mitigated). `TOKEN_MINT` is required and `verifyMint` refuses to start unless it is an initialized mint (classic or Token-2022), since a wrong address would make every list empty.
  - **TWAB fix that came with it:** several transactions on one token account in the same slot (every busy pool vault) have no order in the data, and sorting them by signature broke the "delta leads to the balance" check, which would have blocked a break's eligibility for good. `twab.ts` now recovers the order from the balance chain (`chainOrder`: each event starts where the previous one ended; a history with a transaction missing is still refused), and `sortEvents` also ties on the owner so the published inputs text has one order.
  - Tested with `test/support/token-ledger.ts`, a pretend token that records transactions in the node's wire shape and keeps its own books (`truth`), also served as a JSON-RPC node. web3.js is the oracle for the request parameters and the response shape (`indexer-reader.test.ts`). The node is made to fail at every call and the database at both write steps, and `indexer-eligibility.test.ts` checks that the planner's root, total weight and `inputs_hash` computed from indexed data equal the ones computed from the books, on a busy pool with same-slot swaps. **Never run against a real node** (the cloud sandbox blocks devnet).
- **Break scheduler** (`src/scheduler/`): creates the next break when the treasury can pay for its worst case. `BreakScheduler.run` starts every run from the chain: (1) every break the chain has and the database lacks is copied into `breaks` with the chain's values (a break made by an interrupted run, or by hand with the keeper key, is picked up; a database with no breaks takes all of them, otherwise only ids after its highest, at most 25 per run; a missing account below `next_break_id` is an error); (2) nothing is created while a break is still selling (`Open` and before `closes_at`, read from the chain, so a stale database cannot cause a second one); (3) the reserve is checked the way the program does it (`policy.ts`: vault balance minus `locked_*`, against `paid × (max_pack_price − spot_price)` and `free × max_pack_price`; `reserveProgress` gives the percent for the public progress bar, and the job says it when it moves); (4) `create_break` is sent for exactly `next_break_id` with `opens_at` = now and `closes_at` = now + `BREAK_WINDOW_SECS`. A resend of the same id is safe because the break account is a PDA of the next id, so once one lands every other attempt at that id is refused. An unknown result is checked against the chain next run; a refusal is waited out for 60 s before the same id is tried again. `templateProblem` reports a configured break the program would refuse (counts, prices, window against the program's own limits) instead of sending it. No funds move: creating a break only locks funds in the treasury; the keeper pays the rent of the break and escrow accounts. Config (all required, no defaults, since they are open decisions): `BREAK_PAID_SPOTS`, `BREAK_FREE_SPOTS`, `BREAK_SPOT_PRICE`, `BREAK_MAX_PACK_PRICE`, `BREAK_PACK_MACHINE` (text up to 32 bytes, or `0x` and 64 hex; `machine.ts`), `BREAK_WINDOW_SECS`; `BREAK_AUTO_CREATE=false` turns off creating but not copying. One break sells at a time, and the next starts when the previous sale ended and the reserve allows it.
  - Tested against the program model, which now also follows `create_break` and the treasury's locks (`test/support/mock-chain.ts`: vault balances, `locked_*`, the funding rule, the PDA of the next id, and the unlock when `fund_purchases` pays out). `scheduler.test.ts` covers the boundary (exactly enough creates, one micro-dollar short waits and the model refuses the same break), one break at a time, lost bookkeeping, unknown results, refusals, a paused program and a changed config; `pipeline-rpc.test.ts` sends `create_break` as a real signed transaction through the RPC client; `app.test.ts` takes an empty chain through scheduler, indexer, pipeline, pack buyer and delivery to `delivered`. The vault balances are read with `solana/token.ts`, checked against a token account written by the real SPL token crate (`spl.account.TokenAccount` in `programs/treasury/instruction-vectors.json`).
- **Fee sweep** (`src/sweep/`, migration 0007): fee SOL -> USDC -> the treasury. `FeeSweeper.run` has two steps, each safe to repeat. **Deposit:** whatever USDC the wallet's associated USDC account holds (at least `SWEEP_MIN_DEPOSIT`) goes into the treasury with `deposit_fees`; nothing is remembered, because a deposit that landed leaves nothing to deposit again and one that did not is simply sent again with the balance that is there (the token program refuses a second spend of the same USDC). The program splits it: the subsidy bucket gets `floor(amount × bps / 10000)`, the holder bucket the rest. A refusal is waited out for 60 s; each confirmed deposit is written to `treasury_events` (unique on `(kind, tx_sig)`). **Swap:** only if a `Swapper` is configured (`swapper.ts`: `quote`, `prepare`, `submit`, `status`, written like the pack buyer's steps). It swaps `min(SOL − SWEEP_KEEP_LAMPORTS, SWEEP_MAX_LAMPORTS)`, not under `SWEEP_MIN_LAMPORTS`, with a floor of the quote less `SWEEP_SLIPPAGE_BPS` (never below the optional `SWEEP_MIN_USDC_PER_SOL` price floor; a quote under it means no swap), and refuses a prepared swap whose amount differs or whose floor is looser than asked. The swap is saved in `fee_swaps` BEFORE it is sent (signature, last valid block height, the signed payload), a partial unique index allows one swap in flight, and a new one is prepared only when the chain says the last landed, reverted or can never land (`expired`); a pending one is sent again as it is, so a restart between saving and sending finds and finishes it. A landed swap is written to `treasury_events`. **No swapper exists yet**: Jupiter is a mainnet service and this project is devnet only, so `SWEEP_SWAP_PROVIDER` has only `none` and the sweep deposits USDC that is already in the wallet (on devnet, test USDC the operator sends to the keeper). The wallet is the keeper's (`chain` signs as the keeper); the job is only built when `SWEEP_ENABLED=true` (default off, since it moves money), and the USDC account must exist (a missing one is reported, not created).
  - **Open (needs the owner):** how fee money gets from the Squads multisig into the keeper's wallet (a multisig-approved transfer, or a Squads spending limit for the keeper; the keeper side of that is not built because the Squads instruction layout cannot be checked from here); whether the keeper's key should hold fee money at all, or a separate sweeper key should (it would be a second hot wallet, like the buyer wallet, and the guardrails say authorities belong to the multisig); the real Jupiter adapter (mainnet only, after an audit and the owner's go-ahead). The swap limits above are placeholders until then.
  - Tested against the program model (now also `deposit_fees`, SOL balances and USDC accounts) and a pretend swapper (`test/support/mock-swapper.ts`: lands, never arrives, reverts, is held, expires). `fee-sweep.test.ts` covers the split and its remainder, minimums, refusals, a deposit whose confirmation was lost (landed or not), the swap amount and cap, the floor, that the swap is saved before it is sent, that only one is in flight, a restart in the middle, a competing process, an expired and a reverted swap, and a swap that would give back too little. `pipeline-rpc.test.ts` sends `deposit_fees` as a real signed transaction; `wallet-reader.test.ts` checks `getBalance` against web3.js; `app.test.ts` takes $200 in the keeper's USDC account to the treasury (70/30) and then to a break created by the scheduler.
- **Real RPC client** (`src/solana/{transaction,keypair,rpc,cluster}.ts`, `src/pipeline/rpc-chain.ts`): the `ChainClient` against a Solana node. `transaction.ts` compiles instructions into a legacy message (fee payer first, then signers, then the rest, writable before read-only, each in order of first use; flags merged for an account used twice), signs it and refuses one that needs a signature we do not hold or that is over 1232 bytes. `keypair.ts` loads the keeper key from a Solana CLI keypair file (`KEEPER_KEYPAIR_PATH`, kept outside the repo; the secret never appears in an error or log). `rpc.ts` is a small JSON-RPC client (retries transport failures, 429 and 5xx; not a node's own error). `RpcChainClient.sendAndConfirm` answers `confirmed` only when the node says the transaction landed and succeeded at the configured commitment (`SOLANA_COMMITMENT`, default `confirmed`), `failed` only when the chain did not change (preflight refused it, it landed and reverted, or its blockhash expired and a last look through history found nothing), and `unknown` otherwise; it re-sends the same signed transaction while it has not landed, names the program's error from the log when it can, and after a confirmed send asks for data at least as new as that slot (`minContextSlot`). An RPC outage before anything was sent is an exception, not `unknown`. **Devnet only is enforced against the network, not just the config:** `connect` asks the node for its genesis hash and refuses mainnet-beta and testnet whatever `SOLANA_CLUSTER` says, and for `devnet` requires the devnet hash (`cluster.ts`). `connectFromConfig` builds the client the keeper runs with.
  - Tested without a network: web3.js (a test-only dependency) is the independent parser and signature verifier of every transaction we build, and `test/pipeline-rpc.test.ts` runs the whole pipeline through the real client against a fake node that decodes each transaction with web3.js, executes it on the program model and serves the accounts back. **Never run against a real node yet** (the cloud sandbox blocks `api.devnet.solana.com`), and the three genesis hashes in `cluster.ts` were written from memory: confirm them with `solana genesis-hash -u devnet` (and mainnet-beta, testnet) before the first run.
- **Jobs wiring** (`src/app.ts`, `src/run.ts`, `src/index.ts`): `pnpm --filter keeper dev` (or `build` then `start`) runs the keeper. `index.ts` loads the config, **connects to the node first** (genesis hash check, devnet only; the key is loaded and checked there too), reaches the database, then `buildJobs` and starts the loop. `buildJobs` refuses to start if the database lacks a migration (`checkSchema` names the missing table, column or the `drawn` status), refuses a key that is not the breaks program's keeper (`verifyKeeperIdentity`; if the program is not initialized yet it only warns), checks that `TOKEN_MINT` is an initialized mint (`verifyMint`), and then builds up to six jobs, each starting from what it reads and not from shared memory: `indexer` (balance events and `indexer_state`), `scheduler` (creates breaks and copies them into the database), `fee-sweep` (only when `SWEEP_ENABLED`), `pipeline` (on-chain steps and the status mirror), `pack-buyer` (packs of `Funded` breaks) and `delivery` (cards of `Drawn` breaks). `run.ts` (`startLoop`) never overlaps ticks, and shutdown (SIGINT/SIGTERM) waits for the tick in progress before closing the database pool. Stores are the SQL ones over a `pg` pool (`sqlFromPool`). `DrawnBreaks` copies a verified break's spots from the chain into `spots` before delivering (`BreakRepo.recordSpots`): deliveries refer to those rows, and a row that already says something different is an error, since the chain is the truth.
  - **Config** (`.env.example`): `BREAKS_PROGRAM_ID`, `TREASURY_PROGRAM_ID`, `VRF_PROGRAM_ID` (ORAO by default; must be the program the breaks program is configured with), `ORAO_TREASURY` (ORAO's fee treasury, copied by hand from its network state; the keeper does not guess it and an unedited placeholder fails validation), `KEEPER_KEYPAIR_PATH`, `SOLANA_COMMITMENT`, `JOB_TICK_MS`, `JOB_INTERVAL_MS`, `PACK_PROVIDER` / `CARD_TRANSFER` (only `mock` exist), `MOCK_PACK_PRICE`, `MIN_TWAB` (required, no default: an open decision), `WEIGHT_CAP` (optional, pending A2), `INDEXER_SETTLE_SECS`, `TOKEN_MINT` (required; an unedited placeholder fails validation), `INDEXER_INTERVAL_SECS`, `INDEXER_LAG_SECS` (at least 30), `INDEXER_CALLS_PER_RUN`, `INDEXER_PAGE_SIZE`, `INDEXER_CONCURRENCY`, the `BREAK_*` settings of the scheduler, and the `SWEEP_*` settings of the fee sweep (off by default).
  - **Mock mode** is what runs today, and it says so at startup: the mock pack provider keeps its pretend chain in memory (a restart forgets which packs it "bought", so only a break started and finished in one run is coherent), and the mock card transfer treats every card as held by the buyer wallet until it is "sent" (so the pool's holds-the-cards check is vacuous). Nothing real is bought or moved.

## Guardrails for Claude Code
- **Devnet only** until the user explicitly says otherwise after an audit. Collector Crypt is a mainnet service, so the pack buyer runs against a mock on devnet. Real Collector Crypt tests are manual and run by the user.
- Never commit private keys, seed phrases, or API keys. Use `.env` (gitignored) and `.env.example`.
- All admin/authority roles and program upgrade authority → Squads multisig, never a single hot wallet.
- **Exception: the buyer wallet.** It holds only the pack budget funded per break, up to the cap in `fund_purchases`, and has no authority over any program.
- Every program instruction gets tests for success and failure cases before moving on.
- Keeper steps must be idempotent and retry-safe, especially the pack buyer.
- Ask before changing any rule in "Core rules".
